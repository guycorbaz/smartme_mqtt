\chapter{Configuration}
\label{ch:config}

\textbf{\code{config.toml} is the configuration.} It lives in the state directory and holds
every setting \prog has. The environment carries the smart-me credential, which never
descends to disk; \code{SMARTME\_STATE\_DIR}, because a file cannot say where it lives; and
\code{RUST\_LOG}, which has to be readable \emph{before} the configuration is, since raising
the level is what one does to diagnose a configuration that will not load.

\begin{note}
\textbf{You do not have to write this file by hand.} Since story~6.2 the configuration and
confirmation screens exist: open the bridge in a browser, fill the form, check the mapping
and confirm it, and the bridge starts publishing --- without a text editor and without
restarting the container. See section~\ref{sec:screens}.

This chapter still documents the file, because the file \emph{is} the configuration: the
screens write it, and reading it is how you find out what a running bridge was told. A
headless bring-up (section~\ref{sec:headless}) writes it directly, and is still supported.
\end{note}

The two sources have no setting in common, and that is deliberate. Any overlap would need
a rule about which wins, and such a rule is a place where one source loses silently ---
a value changed in the browser reverting at the next restart to a forgotten line in
\code{.env}, with no error and nothing in the log.

\begin{warning}
\textbf{Eleven environment variables were withdrawn on 2026-08-04} and setting them now
does nothing at all: \code{SMARTME\_GROUP\_ID}, \code{SMARTME\_NODE\_ID},
\code{SMARTME\_BROKER\_HOST}, \code{SMARTME\_BROKER\_PORT}, \code{SMARTME\_METER\_ID},
\code{SMARTME\_DEVICE\_ID}, \code{SMARTME\_SERIAL}, \code{SMARTME\_PUBLISH\_PERIOD\_SECS},
\code{SMARTME\_API\_BASE}, \code{SMARTME\_LOG\_DIR} and \code{SMARTME\_LOG\_KEEP}. They are
all keys in \code{config.toml} now. See section~\ref{sec:configfile}, and
\code{docs/adr/0023-the-file-is-the-configuration-the-credential-stays-in-the-environment.md}
for why.
\end{warning}

\section{The configuration file}
\label{sec:configfile}

\code{config.toml} sits in the state directory --- \code{/data} unless
\code{SMARTME\_STATE\_DIR} says otherwise --- beside \code{bdseq.toml}. Nothing secret is
in it, so it can be read for diagnosis without privileges: checking which topic a meter
maps to has never needed \code{sudo}, and now provably cannot.

\begin{lstlisting}
schema_version      = 5

group_id            = "Plant"
node_id             = "Bridge01"
broker_host         = "mqtt.example.lan"
broker_port         = 1883
publish_period_secs = 30
mapping_confirmed   = true
ui_port             = 8080

# Optional.
api_base = "https://api.smart-me.com"
log_dir  = "/data/logs"
log_keep = 7

[[meters]]
meter_id  = "garage"
device_id = "a1a1a1a1-b2b2-c3c3-d4d4-000000000001"
serial    = "9202685"
enabled   = true
priority  = true   # one of the meters you actually care about
\end{lstlisting}

\begin{note}
\code{created\_ms} and \code{last\_change\_ms} are absent above because \prog writes them,
not you --- they appear the first time it saves this file. They are what the state screen's
context line reads: \emph{``created three weeks ago, last changed two days ago, 4 meters, 2
of them marked as mattering''}. A file that has no dates says so rather than showing the
file's modification time, which a \code{docker cp} or a restore would move.
\end{note}

\subsection{Nothing is published until you confirm the mapping}
\label{sec:confirm}

\prog will not publish anything until a human has looked at the meter→topic mapping and said it is
right. Until then it starts, serves the web UI, and opens \textbf{no MQTT session at all} --- no
connection, no birth, nothing on the broker.

\begin{lstlisting}
mapping_confirmed = false   # nothing is published
mapping_confirmed = true    # a human has checked the mapping
\end{lstlisting}

\begin{warning}
\textbf{This is the error validation cannot catch, and half of it is still yours alone.} \prog
refuses a \code{meter\_id} that cannot be a topic level, two meters that would collide on one topic, and
--- since 2026-08-09 --- a \code{serial} that is not the serial the paired \code{device\_id}
actually reports (section~\ref{sec:serialmustmatch}). What none of that can tell you is that
\code{garage} is pointed at the cellar's meter \emph{consistently}: serial and device id both
the cellar's, only the name wrong. That configuration is well-formed, unique, complete,
self-consistent --- and wrong, and every reading it publishes will be filed under the wrong
room for as long as it runs.

Only you can see that one, and only by reading the serial beside the topic. It is what this
confirmation is for --- and since contract~13 it is also what the \code{serie} property in the
device BIRTH is for: the wire now names the measuring point, so the serial travels beside it and
you can check the pairing from the tag browser as well as from this screen.

And the cost of not seeing it is not a restart. A SCADA host \emph{persists what it discovers}: the
tag folder outlives the process, has to be deleted by hand, and deleting it discards the alarm and
history configuration of everything beneath it.
\end{warning}

\textbf{Changing the mapping withdraws the confirmation automatically.} Adding, removing, enabling
or disabling a meter, or editing its name, device or serial, sets \code{mapping\_confirmed} back to
\code{false}. \textbf{So does changing \code{group\_id} or \code{node\_id}}: both appear in every
topic the bridge publishes, so changing one moves every device to a namespace nobody has looked
at --- which is the same thing as re-mapping them all. Changing something that is not the mapping
--- the publish period, the broker, the log settings --- does not, because it costs you a click
for a change you can already see is unrelated, and a guard that fires for no visible reason is a
guard that gets switched off.

\begin{note}
\textbf{Writing the file by hand counts as confirming it.} A headless bring-up sets
\code{mapping\_confirmed = true} itself: typing the mapping out \emph{is} having looked at it. The
key is a plain boolean for exactly this reason --- a checksum would have been harder to forge and
impossible to write, which would have made the documented bring-up path impossible.
\end{note}

\subsection{The first run: no file is not an error}

A fresh deployment has no \code{config.toml}, and every setting but the credential arrives
through a browser. So \prog \textbf{starts anyway}: it comes up, serves the web UI, and
opens \emph{no} MQTT session --- no CONNECT, no will registered, no NBIRTH, nothing
published --- until a configuration exists. It says so in the log, naming the path where
the file will be written.

A configuration that exists but is \emph{unconfirmed} looks similar from outside and is a different
problem: \prog says so in different words, because one of the two is a click away from being fixed
and the other is not. See section~\ref{sec:confirm}.

That is not the same as a configuration that exists and is wrong. \textbf{A file that is
present and invalid makes \prog refuse to publish} --- no connection, no birth, nothing on
the wire --- while it stays up and lists every fault at once, on the configuration screen and
in the log (chapter~\ref{ch:trouble}). Absence is not invalidity, and neither is a reason to
exit: the screen that writes the first configuration, and the screen that repairs a broken
one, are the same screen, and a process that had exited would be sitting in front of both.

\prog never writes a configuration it invented. A first run leaves the state directory
untouched --- defaults nobody chose are still nobody's configuration.

\subsection{Bringing one up without a browser}
\label{sec:headless}

Write the file by hand. It is a documented format with a version field, which is a better
headless surface than eleven environment variables ever were: put the file in the state
directory, set the credential in \code{.env}, and start the container. Remember
\code{mapping\_confirmed = true} --- typing the mapping out \emph{is} having looked at it,
and without the key the bridge comes up, serves its page, and stays silent.

\subsection{The schema version, what migrates, and what is refused}

\code{schema\_version} exists so that ``this build does not understand this file'' is
\emph{detectable}. Any key \prog does not recognise is refused, and so is any version it
cannot account for.

That first rule matters more than it looks. The library default is to ignore unknown keys
and let missing ones take a default value, so a renamed key would read as \emph{absent},
quietly take its default, and \prog would run happily on a configuration nobody wrote ---
publishing every 30 seconds because the period had silently reverted.

\textbf{Since version 5 there is one migration, and its shape says what a migration may be.}
A version-4 file reads: the three keys version 5 added --- \code{created\_ms},
\code{last\_change\_ms} and \code{priority} --- take the values that are true of a file
written before they existed, which is \emph{unknown}, \emph{unknown}, and \emph{not
marked}. Nothing is guessed at, which is the condition. The file is not rewritten when it is
read; it becomes a version-5 file the next time you save. Anything older than 4 is still
refused, and so is anything from a later build --- that file carries keys this one has no
representation for.

Refusing to \emph{read} such a file is not the same as refusing to \emph{replace} it, and the
two are decided separately. The configuration screen may overwrite a file whose version is
older than the running build's, because the operator is replacing it wholesale with a document
the build wrote itself. It may not overwrite one whose version is \emph{newer}: that file came
from a later image and carries keys this build has no representation for, so writing over it
would drop them without saying so.

\subsection{What a change costs}
\label{sec:changecost}

Not every setting can be adopted by a running bridge, and the ones that cannot must say so
rather than report a success that did not happen. \prog classifies every field, and the
classification is enforced by the compiler --- a new setting stops the build until someone
decides which row of this table it belongs in.

\begin{center}
\begin{tabular}{@{}l p{8.2cm}@{}}
\toprule
\textbf{Cost} & \textbf{What you see} \\
\midrule
Hot & Nothing. The change is simply in force. \\
Device certificate & A \code{DDEATH} and/or \code{DBIRTH} for \emph{one} meter, in the same session, under the same \code{bdSeq}. The node does not blink and the other meters are untouched. \\
New session & The node disconnects and comes back: \code{NDEATH}, a new \code{bdSeq}, \code{NBIRTH}. \\
Process restart & Nothing until the container is restarted. \\
\bottomrule
\end{tabular}
\end{center}

\begin{table}[htbp]
\centering
\caption{Which setting costs what.}
\label{tab:changecost}
\begin{tabular}{@{}>{\ttfamily}l l@{}}
\toprule
\normalfont\textbf{Setting} & \textbf{Cost} \\
\midrule
publish\_period\_secs   & Hot \\
api\_base               & Process restart \\

\begin{note}
Enabling a meter publishes a \code{DBIRTH} and disabling one publishes a \code{DDEATH},
both without disturbing the session. This is conformant, not a convenience: the
specification permits a \code{DBIRTH} mid-session provided the \code{NBIRTH} went out in
the same session, and it \emph{requires} a \code{DDEATH} whenever a device can no longer
provide real-time information --- which is exactly what a meter you have just switched off
is. Stopping quietly would leave its last reading on the host's screen looking current.
\end{note}

\begin{warning}
\textbf{Only the publish period and the staleness policy are genuinely hot today.}
\code{api\_base}, the HTTP timeout and a meter's \code{device\_id} were listed as hot until a
review on 2026-08-04 found they were not: the client that holds them is built once, before the
polling starts, and nothing rebuilds it. They are process-restart settings, and \prog says so
rather than reporting a change it did not make (issue~\#52).

\textbf{A new-session change is currently saved but not carried out} (issue~\#49). \prog
records it, reports it, and keeps the session it has until it is restarted. What it will
never do is claim otherwise: the running configuration it reports back is what is
\emph{in force}, not what was last saved.
\end{warning}

\section{smart-me authentication}
\label{sec:smartme-auth}

smart-me offers several authentication mechanisms. \prog uses the one designed for
headless devices.

\subsection{The available mechanisms}
\begin{itemize}
  \item \textbf{OAuth “Device (Client Credentials)” app} — described by smart-me as
        \emph{“a replacement for basic authentication in embedded devices\dots\ supports
        only the OAuth flow client credentials.”} This is a non-interactive
        machine-to-machine flow — exactly what a 24/7 daemon needs.
  \item \textbf{OAuth Confidential / Public apps} — use interactive flows
        (authorization-code~+~PKCE, device-code, implicit) that require a human to log in
        and consent. Not suitable for an unattended bridge.
  \item \textbf{HTTP Basic auth} — the smart-me account username and password.
\end{itemize}

\subsection{What \prog uses}
\begin{description}[style=nextline]
  \item[Primary — OAuth2 Client Credentials] The bridge exchanges a Client~ID and Client
        Secret for a bearer token, then calls the API with
        \code{Authorization: Bearer <token>}, refreshing the token on expiry.
  \item[Fallback — HTTP Basic] Account user/password. \textbf{Designed, implemented in the
        client library, and not reachable from the environment} --- see the warning below.
\end{description}

\begin{warning}
\textbf{The Basic fallback cannot currently be selected.} \code{smart-me-client} implements
it, but the binary builds OAuth client-credentials unconditionally and never constructs
Basic credentials, so \code{SMARTME\_BASIC\_USER} and \code{SMARTME\_BASIC\_PASSWORD} have
no effect whatever. Worse for anyone relying on the word \emph{fallback}: the OAuth pair is
\emph{required}, so setting the Basic pair \emph{instead} of it makes \prog refuse to publish
with \code{smart-me client id (environment: SMARTME\_CLIENT\_ID): is missing or empty}.
Treat client credentials as
the only way in until this is either wired up or dropped from the design.
\end{warning}

\begin{note}
This decision — client credentials primary, Basic fallback, TLS mandatory — is recorded
in \code{docs/adr/0009-smartme-auth-client-credentials.md}. It supersedes the earlier
\code{Authorization: ApiKey} assumption.
\end{note}

\subsection{Configuring it}
Create a \emph{Device (Client Credentials)} OAuth app in the smart-me portal
(\href{https://api.smart-me.com/swagger}{api.smart-me.com}), copy its Client~ID and
secret, and set them in \code{.env}:

\begin{lstlisting}[language=bash]
# smart-me credentials -- LOCAL ONLY, never commit (.env is gitignored, perms 0600)
SMARTME_CLIENT_ID=your-client-id
SMARTME_CLIENT_SECRET=your-client-secret

# HTTP Basic fallback -- RESERVED, and NOT read by the bridge today.
# Setting these has no effect; the OAuth pair above is still required.
# SMARTME_BASIC_USER=your-account-user
# SMARTME_BASIC_PASSWORD=your-account-password
\end{lstlisting}

\begin{warning}
If the client secret is lost or leaked, smart-me does not allow rotating it in place: the
OAuth app must be deleted and recreated. All smart-me traffic is over TLS and hard-fails
if TLS is unavailable.
\end{warning}

\subsection{Scopes: what an app is allowed to do}
\label{sec:smartme-scopes}

An app's power comes from the \emph{claims} granted to it when it is created, not from the
\code{scope} parameter sent at token exchange. A token request may only ask for claims the
app already holds; asking for more is refused.

\begin{warning}
Do not take the scope list from the OpenID discovery document
(\code{/.well-known/openid-configuration}). It advertises only \code{openid} and
\code{offline\_access}, which is incomplete to the point of being misleading — the real
vocabulary is twelve claims. Read it instead from the OAuth2 security scheme in
\code{https://api.smart-me.com/swagger/v1/swagger.json}, or live from
\code{GET /oauth/claimtree}, which also returns the hierarchy.
\end{warning}

The claims form a tree, and \textbf{a parent implies its children}. Granting
\code{device.readswitch} therefore also grants \code{device.read} — a switching app is
always also a reading app, and there is no claim that permits switching \emph{without}
reading.

\begin{center}
\begin{tabular}{@{}>{\ttfamily}l p{7.6cm}@{}}
\toprule
\normalfont\textbf{Claim} & \textbf{Grants} \\
\midrule
device.readwrite      & Read, control outputs, and add/update values \\
\quad device.readswitch & Read and control the outputs (the relay) \\
\quad\quad device.read  & Read device data only \\
user.readwrite        & Read and write the user settings \\
\quad user.read       & Read the user settings \\
auditlog.read         & Read the audit log \\
realtimeapi.readwrite & Read and write realtime-API registrations \\
\quad realtimeapi.read & Read realtime-API registrations \\
partner.write         & Read and write a partner's devices \\
\quad partner.read    & Read a partner's devices \\
partner.updatefirmware & Update the firmware of all a partner's devices \\
oauthapp.write        & Create and change OAuth applications \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Creating a read-only app (what \prog needs)}

\prog only ever reads. Grant it \code{device.read} and nothing else: a bridge that cannot
switch a relay cannot switch one by accident, and a leaked secret cannot be used to act on
the installation.

\begin{enumerate}
  \item In the smart-me portal, create an OAuth application of type
        \emph{Device (Client Credentials)}.
  \item Give it a name that says where it runs (for example \code{gateway}).
  \item Grant the single claim \code{device.read}.
  \item Copy the Client~ID and secret into \code{.env} as shown above.
\end{enumerate}

\paragraph{Verifying that it really is read-only.} This can be proved without attempting a
write, because the token endpoint distinguishes the two failure modes:

\begin{lstlisting}[language=bash]
# Ask for a claim the app should NOT have.
curl -s -X POST https://api.smart-me.com/oauth/token \
  -d grant_type=client_credentials \
  -d client_id="$ID" -d client_secret="$SECRET" \
  -d scope=device.readswitch
\end{lstlisting}

\begin{description}[style=nextline]
  \item[\code{invalid\_request} — \emph{“This client application is not allowed to use the
        specified scope.”}] The claim exists and the app does not hold it. This is the
        expected answer for a read-only app, and it is a positive result.
  \item[\code{invalid\_scope}] The claim name does not exist. You have made a typo, and the
        test has proved nothing.
  \item[A token is returned] The app \emph{can} switch outputs. It is not read-only.
\end{description}

\begin{note}
Run this against the credentials actually deployed, not against the ones you meant to
deploy. The distinction between the two error codes is what makes the check meaningful: a
test that cannot tell “refused” from “misspelled” always passes.
\end{note}

\subsection{Creating an app that can command a meter relay}

\begin{warning}
\prog does not use this, and does not implement any command path. The bridge publishes
measurements and answers Sparkplug \code{NCMD} \code{Node Control/Rebirth}; it never writes
to smart-me. This section documents the smart-me side so that the capability can be
enabled deliberately — it is not a description of current behaviour. The corresponding
Sparkplug \code{DCMD} question is tracked as issue~\#38.
\end{warning}

Create a second, \emph{separate} Device app granted \code{device.readswitch}. Keep it
separate from the bridge's read-only app: the two have different blast radii, and only one
of them is worth protecting carefully.

\paragraph{1 — Find the device's actions.} Not every meter has a switchable output. Ask
before assuming:

\begin{lstlisting}[language=bash]
curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.smart-me.com/actions/<device-uuid>
\end{lstlisting}

A meter with no relay returns \code{[]}. A meter with one returns its actions, and the
\code{ObisCode} is the identifier you will command:

\begin{lstlisting}
[{"Name":"Relais","ObisCode":"63000C0102FF","ActionType":0}]
\end{lstlisting}

\paragraph{2 — Send the command.}

\begin{lstlisting}[language=bash]
curl -s -X POST https://api.smart-me.com/actions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"deviceID":"<device-uuid>",
       "actions":[{"obisCode":"63000C0102FF","value":1}]}'
\end{lstlisting}

\begin{note}
\code{PUT /Devices/\{id\}} also switches an output and still works, but smart-me's own
specification says of it: \emph{“For new implementations please use the \code{actions}
command.”} Prefer \code{POST /actions}.
\end{note}

\begin{tip}
\code{GET /actions/\{id\}} needs only \code{device.read}, so you can inventory which meters
have a relay using the bridge's existing read-only credentials, before creating any app
that can actually operate one.
\end{tip}

\section{MQTT broker connection}
\label{sec:broker-config}

\prog connects to an \emph{external} broker; it does not embed one. Host and port are
settings in \code{config.toml}, set from the configuration screen or written by hand
(see page~\pageref{ch:config}):

\begin{lstlisting}
broker_host = "mqtt.example.lan"   # host or IP of your broker
broker_port = 1883                 # optional; defaults to 1883
\end{lstlisting}

\begin{note}
Changing either \textbf{costs a new Sparkplug session} --- see
table~\ref{tab:changecost}. \prog keeps the session it has until it is restarted.
\end{note}

A port that is not a number makes the bridge refuse to publish. It does not fall back to
\code{1883} silently --- connecting to a different broker than intended is precisely the
kind of quiet wrong answer this project avoids.

\subsection{Authentication and transport security}

Both are \textbf{planned and optional} --- the broker connection may be secured with TLS
and/or authentication, or left plain, per configuration (FR43, NFR16). Neither is
implemented in the current build.

\begin{warning}
As of this build the broker connection is \textbf{plain and unauthenticated}. \prog
therefore expects its broker to sit on a \textbf{trusted internal network}, reachable only
from hosts you control. Traffic to the \emph{smart-me cloud} is unaffected and remains
TLS-only, hard-failing if TLS is unavailable --- the two paths use different TLS stacks
and only the broker one is disabled.
\end{warning}

\subsubsection*{Why optional rather than mandatory}

A homelab broker is usually shared. It commonly serves devices --- older sensors,
closed-firmware appliances --- that cannot present credentials at all, so a bridge that
\emph{required} authentication would either force the broker into a configuration its
other clients cannot meet, or force a second broker into existence. Enabling
authentication is a decision about the whole broker, not about this bridge, and \prog
follows it rather than driving it.

\subsubsection*{Reserved settings}

The variable names are reserved now so that enabling authentication later is a
configuration change rather than a migration:

\begin{lstlisting}[language=bash]
# Broker authentication -- reserved, not yet honoured by the bridge
# SMARTME_BROKER_USER=
# SMARTME_BROKER_PASSWORD=
\end{lstlisting}

\begin{note}
Broker credentials will follow the same discipline as the smart-me ones: \code{.env} only,
never logged, never in a committed file (NFR16).
\end{note}

\subsubsection*{Authentication and TLS are worth landing together}

MQTT carries username and password \emph{in the clear} inside the CONNECT packet. On a
plain connection, enabling authentication protects against an accidental or careless
client on the same network, but not against anyone able to observe the traffic --- they
would simply read the credentials as they go past. On a trusted LAN that is still a real
improvement; treating it as confidentiality is not.

Broker TLS is currently blocked upstream: the MQTT client's default TLS stack pinned a
transitive dependency carrying unfixed advisories that could not be upgraded past its own
requirement, so it was disabled rather than shipped unused. When that upgrade lands, TLS
and authentication are best enabled in the same change.

\subsection{Sparkplug identity}

The group and edge-node identifiers are \textbf{required}. There is no default, and
\prog refuses to publish without them:

\begin{lstlisting}
group_id = "<your group>"
node_id  = "<your node>"
\end{lstlisting}

\begin{warning}
These form the topic grammar, which is a \emph{versioned contract} (chapter~\ref{ch:contract}).
Changing them after a SCADA has begun historising the tags breaks the continuity of its
stored curves --- the history stays under the old topic and the new one starts empty.
Choose them before the first production run, not after.

\textbf{And a Sparkplug host persists what it discovers.} The group you name becomes a
folder in the host's tag tree that outlives the process and has to be deleted by hand ---
and deleting those tags also discards their alarm and history configuration. Publishing
into the wrong namespace is not undone by restarting with better settings, which is why
these have no default at all: they defaulted to \code{Site} and \code{Bridge} until
2026-07-31, so a \prog started with no configuration published straight into the namespace
most likely to be the production one.
\end{warning}

\section{Meter-to-topic mapping}
Each \code{[[meters]]} table maps one smart-me device onto one Sparkplug device.
\textbf{\code{meter\_id} becomes the device level of the topic}; \code{serial} is what the
bridge holds smart-me to and publishes as a property of the device BIRTH; \code{device\_id} is
the smart-me UUID that is actually polled and never appears on the wire.

\begin{warning}
\textbf{This reversed at contract~13, on 2026-08-25.} Until then the \code{serial} was the
device level and \code{meter\_id} was a purely local label --- and this section said so, having
already been corrected once in the other direction on 2026-08-09. What decided it is not a
preference for readable names: \emph{what a supervisor historises is a measuring point, not a
box}, so a device id built on the serial makes a replaced meter into a new device and breaks the
series at the moment nothing changed for you.

So a SCADA host now browses \emph{meter names}:

\begin{lstlisting}
energie/smartme-bridge/cpt01/puissance
energie/smartme-bridge/cpt02/energie
\end{lstlisting}

\textbf{Choose \code{meter\_id} as carefully as you would a tag name}, because it is one:
renaming it later orphans every series a host has recorded under the old one. That is why
\prog{} classifies a rename as needing a restart, and why it buries the old device on the wire
rather than letting a host go on showing its last value as current.
\end{warning}

Two meters that would produce the same topic are refused at startup, as is a \code{meter\_id}
that cannot be a topic level at all --- a mapping collision would merge two meters' histories
into one curve, which is not recoverable by fixing the configuration afterwards.

\subsection{The serial must be the one smart-me reports}
\label{sec:serialmustmatch}

\code{serial} and \code{device\_id} are two names for the same physical meter, written on the
same row, and \emph{nothing on your side checks that they agree}. They are used at opposite
ends: \code{serial} is what the device is born under on the wire, \code{device\_id} is what
\prog asks smart-me for. If they name different meters, every reading arrives addressed to a
device the host was never told about, and is discarded.

Before 2026-08-09 that was silent in the worst way available. The fetch succeeded, so the
bridge considered the meter fresh, the health check stayed green, the tags appeared in the
tag browser --- and not one value ever reached them. A bridge that looks perfect and publishes
nothing.

\prog now compares the two on every answer smart-me gives. A meter whose reported serial is
not its declared one is marked as a fault, named on \code{/} and in \code{failed\_sources},
and stops rather than polling on. The log line names both serials and the \code{device\_id},
which is enough to tell you which of the two fields is wrong:

\begin{lstlisting}
meter cellar is declared with serial 9202686, but smart-me device
a1a1a1a1-...-000000000001 reports serial 9202685
\end{lstlisting}

\begin{note}
This is a fault a restart clears \emph{after} you fix the file, not one that clears itself:
correcting a serial requires a restart anyway (see the change-cost table above), so the
refusal and the repair ask for the same thing.
\end{note}

\section{Editing it in the browser}

Everything above can be typed into the file by hand, and everything above is also a field on
\code{/config}. The screen writes the same file, through the same validation: a submission that
would produce a configuration \prog cannot use is refused \emph{with every fault named beside
its own field}, and nothing is written.

\begin{note}
\textbf{There is no credential field, and its absence is the design.} \code{SMARTME\_CLIENT\_ID}
and \code{SMARTME\_CLIENT\_SECRET} live in the environment; a field that never renders is a
field that can still be posted to, and the strongest form of \emph{never rendered} is
\emph{never present}.
\end{note}

\textbf{The account's meters can be loaded into the form.} \emph{Load the account's meters}
asks smart-me at the \textbf{saved} API base --- not one typed above and not yet saved --- and
lists what the account has. Picking one fills the device id \emph{and} the serial together,
because those two are the pair \prog verifies on every fetch, and a transcription error in
either is the commonest way to point a meter at the wrong device. Picking saves nothing and
publishes nothing.

\textbf{Meters you care about can be marked.} A tick beside a meter records that it is one of
yours that matters; it changes nothing about what is published, and it is counted on the state
screen so that during an incident you can see at a glance whether the affected meters are the
ones you mind about. \prog cannot deduce this: smart-me reports an id, a name, a serial and two
numbers --- no make, no model.

\section{The first run: nothing is published until you confirm}
\label{sec:confirmscreen}

A configuration that is merely valid is not one a human has looked at. On a first run --- and
after any edit that changes what would be published --- \prog opens \textbf{no MQTT session at
all} until the mapping is confirmed: no connection, no birth, nothing on the broker.

The confirmation screen shows, for every meter, \textbf{the exact topic it would publish on},
built by the publisher's own code rather than spelled out by the page. What you are confirming
is that each logical name points at the device you think it does.

\begin{note}
\textbf{The click carries a fingerprint of the mapping it saw.} If the file changes between the
screen rendering and your clicking --- another window, a hand edit --- the confirmation is
refused rather than applied to a mapping nobody reviewed.
\end{note}

\begin{note}
\textbf{Editing the mapping withdraws the confirmation automatically}, and so does editing
\code{group\_id} or \code{node\_id}, which appear in every topic. Editing anything else does
not: changing the broker port or the log retention is not a claim about which meter is which.
\end{note}

\section{Poll interval, logging, and retention}

\code{publish\_period\_secs} is bounded at both ends and there is deliberately no value
meaning ``off''. The minimum of 5 seconds keeps \prog from becoming a load generator
against a cloud whose meters do not update that fast. The maximum of 300 is not a
preference: the periodic publish is the mechanism by which a SCADA host that restarted
notices a node whose BIRTH it never saw and asks for a rebirth, so a period of ``never''
would not slow that repair down --- it would remove it.

A change takes effect on the next tick, with nothing disturbed on the wire.

\subsection{Logging to a file}

The console always receives every line. File logging is \emph{additional} and opt-in: with
\code{log\_dir} unset there is no log file at all, and \prog behaves exactly as it did
before file logging existed.

\begin{lstlisting}
# Turns file logging ON. Written as smartme_mqtt.<YYYY-MM-DD>.log, rotated daily.
log_dir = "/data/logs"

# How many rotated files to keep. Default 7 (one week).
log_keep = 7
\end{lstlisting}

\code{log\_keep} must be a positive whole number. A value that is not one is refused rather
than guessed at: \prog says so on stderr and keeps 7.

\begin{warning}
\textbf{These two are the one pair that a running \prog cannot adopt.} The logging
subscriber is built before the configuration is read --- it has to be, or a fault in the
configuration would have nowhere to be reported --- and it cannot be re-pointed afterwards.
Changing them is saved and takes effect at the \emph{next} start, and \prog says so rather
than reporting a success it did not deliver.
\end{warning}

\begin{note}
File logging can never stop the bridge. If the directory cannot be created or the file
cannot be opened, logging degrades to console-only and prints the reason on stderr. In a
container the usual cause is the bind-mount's ownership --- the directory must belong to the
uid the container runs as (10002); see chapter~\ref{ch:install}.
\end{note}

\begin{warning}
Under pressure the \emph{file} loses lines and the console does not. A saturated write
buffer drops log lines rather than blocking the bridge, because a slow disk must never
stall publishing. So \code{docker compose logs} stays complete when the file does not. The
number of lost lines is reported when \prog shuts down, so the loss is never silent --- if
you are reconciling a file against the console, that line is the reason they differ.
\end{warning}

\subsection{Log level}

\code{RUST\_LOG} is the standard \code{tracing} filter and applies to the console and the
file alike. It defaults to \code{info}, deliberately: the library's own default is
\code{error}, which would hide the ignored-command traces, the QoS-downgrade warning and
every traced drop --- an operator would read an empty log as ``nothing happened''.

\begin{lstlisting}[language=bash]
# Default.
RUST_LOG=info

# Raise one subsystem without drowning in the rest.
RUST_LOG=info,smartme_bridge::adapters::mqtt_driver=debug
\end{lstlisting}
