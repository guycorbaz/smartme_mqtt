\chapter{Operations \& the web UI}
\label{ch:ops}

\section{Reaching it}
\label{sec:screens}

The bridge serves a web interface on port \code{8080} \emph{inside} the container --- or on
\code{SMARTME\_UI\_PORT} when that is set \emph{and} no \code{config.toml} exists yet, which is a
development convenience rather than a deployment setting (ADR~0037). It
publishes no host port: the reverse proxy reaches it over a shared Docker network and is the
only thing that can. There is \textbf{no login} --- the trust boundary is the proxy, not this
process.

The interface answers in every state the bridge can be in \emph{once it is running}, and that
is deliberate rather than convenient: since \code{config.toml} became the configuration, a
browser is the only way in, so a server that only ran alongside a healthy session would be
absent from exactly the situations it exists for.

\begin{note}
\textbf{There is no state without a web interface.} A \code{config.toml} that is present and
unusable --- malformed, carrying a key this build does not know, from another schema version,
or unreadable altogether --- does \emph{not} stop the bridge. It comes up, opens no connection
to the broker, emits no birth, publishes nothing, and serves the configuration screen with
every fault rendered against the field it belongs to. \code{/healthz} answers \code{200}, so a
container healthcheck cannot restart away the screen you need.

\textbf{Until 2026-08-06 it refused to start}, and refusing meant no screen --- which made the
commonest first-run mistake, a state directory nobody \code{chown}ed, a restart loop with no
way out that did not involve a shell on the volume. The faults are still printed on
\code{stderr} and in \code{docker compose logs}, each naming the key to edit.

The distinction that matters is \emph{where the repair is}. A file the bridge could read and
rejected is repaired in the form: correct the fields, press \emph{Save}, and the unusable file
is replaced wholesale. A file it could not read \emph{at all} is a filesystem problem --- the
fault says so, and names the \code{chown} --- and no amount of typing in the browser will fix
it, because the bridge cannot write there either.

Correcting the fields and pressing \emph{Save} overwrites the unusable file: a
file this build can diagnose as broken --- malformed TOML, a key it does not know, a
\code{schema\_version} older than its own --- is exactly what the form was rendered from, and
writing it back is the repair.

\textbf{One file is still not overwritten, and deliberately:} one carrying a
\code{schema\_version} \emph{newer} than this build's, which is to say one written by a later
image. It holds settings this build cannot represent, so replacing it would discard them
silently. The refusal names the version, and the answer is to roll the image forward again
rather than to delete the file.
\end{note}

\section{A first run, start to finish}

\begin{enumerate}
  \item Start the container with the credential in \code{.env} and nothing else configured.
        It comes up, publishes nothing, and says so.
  \item Open it in a browser and go to \textbf{Configuration}. Fill in the Sparkplug group
        and node, the broker, the publish period, and at least one meter --- its name, its smart-me
        device id and its serial. Tick \emph{Published}.
  \item Save. If anything is wrong, \textbf{every fault is shown at once}, each beside the
        field it belongs to, in the same words the bridge would have used had it read the
        value from the file. There is one set of rules, not two: a value this form accepts
        is a value the bridge will start on.
  \item Go to \textbf{Confirm the meter mapping}. Check each \textbf{serial against its
        topic}. This is the one error no machine can catch --- a mapping can be
        well-formed, unique, complete and pointed at the wrong meter --- so it is a separate
        page and a separate click, never a checkbox on the save form.
  \item Confirm. The bridge starts publishing. \textbf{You do not restart anything.}
\end{enumerate}

\begin{note}
There is \textbf{no credential field} on any screen, and that is not an oversight: the
smart-me credential lives in the environment and never descends to disk, so the strongest
form of \emph{never rendered} turned out to be \emph{never present}. If a fault names
\code{SMARTME\_CLIENT\_ID} or \code{SMARTME\_CLIENT\_SECRET} it is reported as an
environment problem, not drawn as a box you can type in --- because you cannot fix it here.
\end{note}

\begin{warning}
\textbf{The state directory must be writable by the container's user.} It runs as uid
\code{10002}, so a bind mount created by anyone else is read-only to it and the save will
fail. The screen says so plainly --- \emph{``the configuration was NOT written''} --- and
changes nothing, rather than reporting a success that never reached the disk. The fix is
\code{chown 10002:10002} on the directory, once, before the first run.
\end{warning}

\section{Changing a setting on a running bridge}

Not every setting costs the same, and the screen says which before you believe it happened.
After a save it reports one of four verdicts:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Verdict} & \textbf{What actually happened} \\
\midrule
Saved, and in force now          & The running bridge is already using it \\
One device re-announced          & Same session, same \code{bdSeq}, one fresh DBIRTH \\
Saved --- but NOT in force       & Needs a new Sparkplug session; restart to apply \\
Saved --- but NOT in force       & Needs a process restart; the setting is on disk \\
\bottomrule
\end{tabular}
\end{center}

The distinction is the point. Changing the broker, the group id or the node id is a
\emph{new session} by definition, and this build cannot open one without being restarted.
Changing the web UI port likewise: a listener cannot move without dropping what is connected
to it. The screen names each setting still waiting, and re-reads what is genuinely in force
rather than echoing back what you typed --- so it never reports a change the bridge did not
make.

\begin{warning}
\textbf{Withdrawing a confirmation still costs a restart.} Editing the mapping --- the meters,
or \code{group\_id} or \code{node\_id}, which are in every topic --- clears
\code{mapping\_confirmed}, correctly, since it is a different mapping and nobody has
looked at it. But a bridge that is already publishing keeps its session until it is
restarted. Confirming moves you forward without a restart; going back does not.
\end{warning}

\section{Submissions from elsewhere are refused}

Because there is no login, any page open in your browser could otherwise post to the bridge
if that browser can reach it --- a reconfiguration needs no credential to steal when there
are none. Every submission is therefore checked against the page it claims to come from, and
one that came from somewhere else is refused with \emph{Refused}, changing nothing.

A caller that sends no \code{Origin} at all --- \code{curl}, a script, the container smoke
test --- is allowed: it is not a browser, and refusing it would break the headless path
while stopping no attack. See
\code{docs/adr/0024-the-config-ui-refuses-submissions-from-other-origins.md}.

\section{The meter view: what each meter is doing}

\code{/meters} is one row per meter and nine columns, and it is the page to open when
something is wrong with a meter rather than with the bridge. The columns are, in order:

\begin{center}
\begin{tabular}{@{}>{\bfseries}l p{9.2cm}@{}}
\toprule
\normalfont\textbf{Column} & \textbf{What it says} \\
\midrule
Meter & the logical name, the one that appears in the Sparkplug metric path \\
Serial & the serial from your configuration --- and \emph{no topic is shown without one} \\
Topic & built by the publisher's own code path, so it is the topic the bridge would really
publish on; never spelled out by the page \\
Power, Energy & the last values published, or \code{---}. \textbf{A dash is not a zero}: a
value nobody has published is absent, and a \code{0.000 kW} would be a measurement \\
Reading age & how old the \emph{measurement} is, with the staleness threshold it was judged
against --- e.g.\ \emph{4 minutes ago (stale past 90 s)} \\
Published as & the quality on the wire, with its cause: \code{Bad (credential-rejected)} \\
Last published & every cycle, because \prog publishes a verdict every cycle \\
Last changed & when the meter last measured something \emph{new} \\
Whose fault & \emph{world}, \emph{you} or \emph{bridge}, and the one thing to do about it \\
\bottomrule
\end{tabular}
\end{center}

\begin{note}
\textbf{The pair to read together is \emph{last published} and \emph{last changed}.} A meter
that publishes every ten seconds and last changed an hour ago has stopped measuring; the
bridge has not stopped publishing. Without the pair the two are indistinguishable, because
\prog republishes a verdict on every cycle by design.
\end{note}

\section{Two healths, and which end to look at}

Above the table, one line reports the \textbf{broker}: connected, never connected since this
bridge started, or unreachable since a named instant. It appears on the state screen as well,
in the same words --- a broker that is unreachable and a source that answers nothing produce
the same silence on the wire and call for opposite gestures.

\begin{note}
\textbf{An unreachable broker is not a bridge fault, and the page says so.} Readings are still
judged and their verdicts still stand; what stops is delivery. Restarting \prog repairs nothing
--- which is also why the health endpoint stays \code{200} through it (\S\ref{sec:healthz}).
\end{note}

\section{Whose fault, and what to do about it}

Every fault carries a \textbf{culprit} --- \emph{world}, \emph{you}, \emph{bridge} --- and
the gesture that cause asks for. The three culprits answer \emph{who can repair this}; the
gesture answers \emph{what to do}, and it is written per cause rather than per culprit. A
rejected credential says to set \code{SMARTME\_CLIENT\_ID} and
\code{SMARTME\_CLIENT\_SECRET} and restart; a serial that does not match says to open the
configuration and compare that row against the account. They are different repairs and they
read differently.

\begin{note}
\textbf{No cause ever accuses the bridge.} The oracles judge \emph{readings}, and a reading is
never \prog's fault. \emph{bridge} appears only when \prog lost a reading it had already
accepted --- a full outbox, a refused publish --- and then the gesture is to read the log and
report it.
\end{note}

\section{Checking one meter end to end}

\code{/check} asks smart-me for one meter \emph{now} and shows three links beside each other:

\begin{enumerate}
  \item \textbf{the source} --- a real request, with how long it took, and the numbers the
        account returned. They are shown unconverted and unjudged, and the page says so.
  \item \textbf{the value} --- what \prog is publishing for that meter right now, judged at
        its own last tick.
  \item \textbf{the sink} --- whether the broker is reachable, and what this meter has lost.
\end{enumerate}

\begin{warning}
\textbf{The check publishes nothing, and this is deliberate.} A test value on the wire would be
indistinguishable, in your historian, from a measurement. The third link therefore reports the
broker's \emph{observed} state rather than proving it with a message nobody asked for.
\end{warning}

\begin{note}
\textbf{The first two links can disagree, and the disagreement is the useful part.} A source
that answers while \prog still publishes a fault is a meter latched by something that already
happened --- and the fault names what clears it. The check does not re-judge the reading it
fetches: the freshness and counter oracles judge against a per-meter memory, and a button that
moved it would change what the \emph{next} real cycle publishes.
\end{note}

\section{The configuration context line}

The state screen carries one auto-written line: when this configuration was created, when it
last changed, how many meters it serves and how many of them you marked as mattering. A
configuration written before \prog recorded those dates says \emph{unknown} rather than
showing the file's modification time --- which a \code{docker cp}, a restore or a \code{touch}
would move, and which would then be a plausible date that is nobody's change.

\section{The health endpoint}
\label{sec:healthz}

\code{GET /healthz} is the machine-facing answer and is described with the rest of
diagnosis in chapter~\ref{ch:trouble}. The short version: the \emph{status code} answers
``is this process worth keeping?'' and the \emph{body} answers ``is it doing anything?''.
They are two different questions, and a bridge that is deliberately silent --- unconfigured,
waiting for you to confirm, or holding a configuration it cannot use --- answers \code{200},
because the healthcheck restarts the container and restarting one would destroy the very
screen needed to configure it.

\subsection{A meter that cannot be read is named}

A \emph{fault} is not a deliberate silence, and the two are reported apart. When \prog cannot
get a reading it can vouch for, that meter's name appears on \code{/} --- ``one meter is not
being read: \emph{cellar}'' --- and in \code{/healthz} under \code{failed\_sources}, which is
an empty list when everything is being read.

Two things put a meter there, and they are diagnosed in opposite places:

\begin{itemize}
  \item \textbf{smart-me refused or could not answer} --- typically a rejected credential.
        Check \code{SMARTME\_CLIENT\_ID} and \code{SMARTME\_CLIENT\_SECRET} in the
        environment.
  \item \textbf{the device is not the one declared} --- smart-me answered perfectly, but the
        serial it reports for that \code{device\_id} is not the \code{serial} written beside
        it in the configuration. Nothing is wrong with your credentials; the two fields on
        that row do not describe the same meter. See
        section~\ref{sec:serialmustmatch}.
\end{itemize}

The log names which of the two it was.

\textbf{No value is published for a meter in this state.} That is worth stating plainly,
because the obvious guess is the opposite one: a fault does not fall back to the last known
reading marked not-good. A meter that has never answered has no value to publish, and one
that answered before publishes an explicitly empty reading --- the quality says ``this is not
a reading'', so no number goes with it. Nothing downstream shows a value as current, and
nothing downstream shows an old one either.

The status code stays \code{200}, and that is deliberate rather than lenient: neither fault
is one a restart clears, so returning \code{503} would put the container in a loop and
destroy the screen that names the problem. What a restart \emph{does} fix --- a poll loop
that has stopped looping --- is what \code{503} is reserved for.

Until 2026-08-07 the page said the bridge was ``polling the meters and publishing what it
reads'' whatever the meters were doing, because it had no way to see them.

\subsection{A reading that never reached the broker is counted}
\label{sec:droppedreadings}

A meter can be read perfectly and still lose readings, because the loss happens \emph{after}
the reading is judged: the broker is unreachable, or its outbound queue is full. Nothing on
the wire can report this --- what is being reported is precisely what never reached the wire
--- so \code{/healthz} is the only place it appears, under \code{dropped\_readings}. It is an
empty list when nothing has been lost.

Each entry names the meter, the reason, how many, and whether the meter has since been
switched off:

\begin{verbatim}
"dropped_readings":[{"meter":"appart-est","reason":"outbox-full",
                    "count":2,"retired":false}]
\end{verbatim}

\code{retired} answers the question the count alone cannot: \textbf{is this a live fault, or
the history of a meter you disabled?} A disabled meter's figure is frozen rather than falling,
so without this flag it reads exactly like a fault that stopped getting worse. The counts are
\emph{not} cleared when a meter is disabled --- the readings really were lost, and erasing a
fact is the one thing these surfaces may not do --- so what you get is the number plus the
sentence that explains it. A meter that publishes again is no longer \code{retired}, on its
first reading.

\begin{warning}
\textbf{A meter whose configuration row you \emph{deleted} is not \code{retired}}, and the
difference is deliberate. Deleting a row costs a restart, which the configuration screen tells
you; until you perform it the meter goes on polling and goes on counting
\code{undeclared-device} once per period. That rising count is the restart debt staying
visible, and labelling it as history would hide the one thing you still have to do.
\end{warning}

The counts are cumulative for as long as the process runs --- an outage spanning three
reconnections is one outage --- and they are not cleared by a reconnection. A restart clears
them, because they describe this run. \textbf{They carry no time}, so one reading of
\code{/healthz} cannot tell an outage that is still running from one that healed hours ago;
that takes two readings, a minute apart, and a count that moved between them.

There are six reasons. Between them they cover every way a reading can fail to be
\emph{handed over} --- which is not quite the same as every way it can fail to arrive, and the
difference is stated at the end of this section:

\begin{itemize}
  \item \code{outbox-full} --- the queue \emph{between} the polling tasks and the transport
        task is full: the transport task is alive but is not emptying it. \textbf{Usually a
        broker outage}, because the transport does not empty that queue while it waits between
        reconnection attempts --- but a host sending a burst of Rebirth Requests, or a large
        configuration change, produces it too, since the transport answers those before
        returning to the queue. The log says which.
  \item \code{transport-queue-full} --- the MQTT client's own outbound queue refused the
        message. Same cause, one layer further out.
  \item \code{mqtt-task-gone} --- the transport task has stopped. Every later reading is lost
        too; this one needs the log.
  \item \code{before-birth} --- a reading arrived before the node had announced itself.
        \textbf{A burst of these is normal after every reconnection}, and after every start:
        the readings that accumulated while the broker was away are ready immediately, and the
        new session's announcement takes a network round trip. A burst therefore means the
        connection dropped, not that anything is wrong with the birth. Only a \emph{continuous}
        stream of them, with no reconnection in the log, points at a birth that is not
        completing.
  \item \code{undeclared-device} --- a reading for a device the last birth did not declare.
        Two ways to get here. The ordinary one is a serial that changed underneath a running
        bridge. The other is a birth certificate the outbound queue refused: \prog then
        \emph{withdraws} that device's declaration, precisely so its readings are counted here
        rather than reported as delivered to a host that was never told the device exists. The
        log line naming the partly published birth is what tells the two apart, and the next
        birth --- a reconnection, or the rebirth a host requests when it sees data for a device
        it does not know --- restores the declaration on its own.
  \item \code{unpublishable} --- the reading could not be encoded or addressed at all. This
        one is a defect, not a weather report; the log carries the reason.
\end{itemize}

\textbf{\prog buffers nothing and replays nothing.} A reading lost to an outage is gone, and
the bridge does not re-send it with a new timestamp when the broker returns --- an outage must
read as a gap, never as a burst of fresh data. What comes back is the next reading, with its
own timestamp.

\begin{warning}
\textbf{The count is of readings \prog could not hand over, not of readings the SCADA did not
receive.} The MQTT client accepts a message into its own send queue before it reaches the
network, so a reading counted as delivered here can still be lost with the connection --- and
a reading refused by the SCADA because it never saw the device's announcement is not counted
at all. \textbf{A gap in the historian with \code{dropped\_readings} empty is therefore
possible, and it is not a contradiction.} The counts are a floor on what was lost, never a
ceiling.
\end{warning}

Each loss is also traced at \code{WARN} with the reading's own \code{ValueDate}, so a gap in
the historian can be lined up against the log line for the reading that should have filled
it.

The status code stays \code{200}. A restart cannot reach a broker that is down; it would
loop, and destroy the surface naming the fault.

\subsection{How soon a silent meter is marked stale}
\label{sec:stalenesslatency}

A meter that has been answering and then stops is marked not-good on the wire within
\textbf{one publish period plus one fetch timeout} of its last good reading --- with the shipped
defaults, 30\,s + 10\,s, so about 40 seconds. At the shortest period the bridge accepts (5\,s)
it is about 15 seconds, measured.

The guarantee \prog is held to is looser than that: \emph{no later than} \code{2 × publish
period + the fetch timeout}. The extra period is deliberate slack. It leaves room for a future
change --- a retry inside a tick, say --- without renegotiating the promise, and it is what a
regression is caught against: if the real figure ever doubled, it would still be inside the
promise and the test that measures it prints the number every run.

\begin{note}
\textbf{One meter's outage costs the others nothing.} Each meter is polled by its own task, so a
meter that hangs for the full fetch timeout does not delay any other meter's poll --- the three
that answer keep publishing \code{Good} on their own cadence throughout. That is the whole
reason the runtime is one task per meter rather than one task walking the list.
\end{note}
